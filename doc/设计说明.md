# 送物小车 · 设计说明

写课设报告时可以直接拆着用。这里讲清楚四件事：整个系统怎么搭的、状态机怎么走、
几个关键取舍为什么这么定、哪些地方还能接着做。

---

## 1. 总体结构

```
        ┌─────────────────────────────────────────────┐
        │  操作入口                                    │
        │  cmd_panel.py / rostopic / 触摸屏            │
        └───────────────────┬─────────────────────────┘
                            │ /spark_deliver/command
        ┌───────────────────▼─────────────────────────┐
        │  deliver_node.py  （送物状态机）             │
        │  · 读地点表  · 发导航目标  · 计时  · 播报    │
        └──────┬───────────────┬──────────────┬───────┘
               │ actionlib     │ photo_event  │ /voice/tts
               │ move_base     │              │
    ┌──────────▼──────┐  ┌─────▼───────┐  ┌───▼──────────┐
    │ 已有导航栈       │  │ photo_node  │  │ tts_bridge   │
    │ map_server      │  │ 抓图存盘     │  │ ekho 播报     │
    │ amcl            │  │ meta.jsonl  │  └──────────────┘
    │ move_base       │  │ index.html  │
    └─────────────────┘  └─────────────┘
               ▲                ▲
        激光 / 里程计      相机 /camera/.../image_raw
```

分工的原则是：**业务逻辑和硬件、算法解耦**。

- 送物节点只管“什么时候去哪、什么时候说话、什么时候拍照”，不碰底层
- 导航交给现成的 `move_base`，定位交给 `amcl`，路线规划不用自己写
- 拍照交给独立节点，通过一个事件话题触发；拍照节点挂了不影响送物
- 播报只发文本到 `/voice/tts`，换引擎不用改业务代码

## 2. 状态机

```
        ┌──────┐  收到目的地指令
        │ idle │────────────────┐
        └──────┘                │
           ▲                    ▼
           │             ┌─────────────┐   到达
           │             │  navigating │────────┐
           │             └─────────────┘        │
           │                    │ 失败/超时      ▼
           │                    ▼         ┌──────────┐
           │             ┌──────────┐     │ arrived  │ 触发拍照
           │             │  error   │     └────┬─────┘
           │             └──────────┘          │ 停留 1.5s
           │                                   ▼
           │                            ┌──────────┐
           │            取消            │ waiting  │ 等确认/超时
           └────────────────────────────┤          │
                                        └────┬─────┘
                                             │ 确认 或 超时
                                             ▼
                                        ┌───────────┐
                                        │ returning │
                                        └─────┬─────┘
                                              ▼
                                         ┌──────────┐
                                         │ finished │
                                         └──────────┘
```

几个实现上的点：

- **单工作线程串行执行任务**，同一时刻只跑一单，避免两个目标互相打架
- **取消用 Event 标志 + `cancel_goal()`**，不是杀线程；导航轮询每 0.2 秒检查一次，
  所以取消是“准实时”的
- **导航超时和失败重试分开处理**：超时先 `cancel_goal()` 再等结果回收，
  否则下一次 `send_goal` 会跟上一个目标串线
- **等取件可打断**：`pickup_event.wait(0.2)` 轮询，确认、取消、超时三种情况都能立刻响应

## 3. 关键取舍

**为什么用 actionlib 而不是发 `/move_base_simple/goal`？**
简单目标话题发完就不知道结果了。送物必须知道“到没到”，到了才能播报和拍照，
所以要用带反馈和结果的 action 接口。

**为什么拍照要单独拆一个节点？**
三个理由：一是相机取图有 IO 开销，放在状态机里会拖慢导航轮询；
二是存盘/生成网页可能失败，不能让它把主流程带崩；
三是拆开之后，同一个拍照节点配上 `task:=photo_round` 就能当独立的拍照工具用。

**为什么播报只发文本，不做语音合成？**
工作区里已经有 `/voice/tts` 这个约定（`spark_voice`、`final_project` 都在用）。
沿用它可以和已有节点共存，也不把 ekho/百度/讯飞绑死在业务代码里。
`tts_bridge.py` 只是一个“没有别的 TTS 时的兜底”。

**为什么不改别的功能包？**
送物本质上是在现有能力上做编排，不是重造导航。所有依赖都通过话题、服务、action 走，
现有包一个字节都不用动，出问题也好定位——要么是我的包，要么是现成栈。

**地点表为什么用 YAML 而不是参数服务器？**
地点数量会变，改一个点不该重启一堆节点。YAML 可读、可手改、可以用脚本生成，
`place_manager.py` 直接读写这个文件（不依赖 ROS），跟 `spark_patrol` 的
`waypoints.yaml` 是同一套思路。

**为什么坐标要手动标定，不做自动建点？**
导航点的 x / y / 朝向是场地属性，不是算法能推出来的。自动生成只会在
定位漂移时写进一批错点，反而更难排查。所以工具只管「存 / 改 / 删 / 校验」，
坐标从哪来看 `RViz` 的 `/amcl_pose` 或现场量——责任明确。

**示教模式为什么要「遥控 + 按键」？**
手填数字的门槛不在输入，在于「读得出当前坐标」这件事本身：要开 RViz、找到
`/amcl_pose`、把四元数换算成角度。示教把这一步变成「开到地方按一下空格」，
读数、换算、落盘都由程序做，人只负责把车开对位置——这是人的强项。

**为什么加 reload 服务而不是重启节点？**
地点表和业务节点解耦，但 `deliver_node` 只在启动时读一次，改完必须重启。
示教场景里改表是高频动作，重启一次要重等 AMCL 收敛，体验很差。
`/spark_deliver/reload` 只重读 YAML（几十毫秒），示教工具退出时自动调一次，
闭环就顺了。执行任务期间调用会被拒绝，避免跑一半地点表变了。

## 4. 数据格式

**places.yaml**（初始是空表，点全部由 `place_manager.py` 标）

```yaml
frame_id: map
home:   {name: 出发点, x: 0.0, y: 0.0, yaw: 0.0}
places:
  - name: 前台
    x: 1.2       # 地图坐标，米
    y: 0.5
    yaw: 1.571   # 到达后朝向，弧度（工具里输 90 度，自动换算）
    actions: [deliver, photo]   # deliver=可送物，photo=到点拍照
```

没有地点时 `places: []`，节点照常启动，只是警告一句并提示怎么加。

**meta.jsonl**（每行一条，追加写，不会因为并发写坏整个文件）

```json
{"file": "2026-11-02/143012_前台.jpg", "place": "前台", "tag": "arrive",
 "stamp": 1793590132.5, "time": "2026-11-02 14:30:12"}
```

**status**（latched，晚订阅的节点也能立刻拿到当前状态）

```json
{"state": "waiting", "text": "等待取件", "place": "前台",
 "busy": true, "places": ["前台", "会议室"]}
```

## 5. 实测记录

用 `sim_nav_server.py` + `sim_camera.py` 在无真机条件下跑通的完整流程：

| 时间 | 事件 |
|---|---|
| 11:28:51 | 收到指令，播报“出发，送往前台”，发出导航目标 (1.0, 0.5) |
| 11:28:54 | 到达，触发拍照（tag=arrive），播报“请取走” |
| 11:28:59 | 等待 5 秒无人确认，播报“没人来取，我先回去了” |
| 11:29:00 | 回到出发点，状态 finished |
| 11:29:12 | 巡拍模式启动，依次到前台、会议室拍照 |
| 11:29:19 | 巡拍结束，共 2 张，回到出发点 |

另外单独验证过两条分支：

- **提前确认**：状态 `waiting` 时按确认，6 秒内返航（没有等满 30 秒超时）
- **中途取消**：导航中调用 cancel，状态立刻回 `idle`

## 6. 还能怎么往下做

按“改动小、效果明显”的顺序排：

1. **取件检测自动化**：现在靠按键确认，可以接深度相机看平台上东西还在不在，
   东西没了就自动返航，省掉人工确认
2. **多单排队**：现在是串行单任务，可以加一个任务队列，连续送几个点
3. **到达精度**：move_base 默认容差 0.1m 左右，如果要求停得很准，
   可以加一段视觉伺服（识别地面标记再微调），这也是自动回充的前置技术
4. **网页加筛选**：照片多了以后按地点/日期筛选，或者做成一个小服务远程看
5. **异常上报**：送不到的时候发一条消息（邮件/微信）而不是只播报
